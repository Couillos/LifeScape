PLAN DE DÉVELOPPEMENT — MARCHÉ QUI S'ÉQUILIBRE (exécution de docs/plan-equilibre.txt)
=====================================================================================
Date : 2026-11-19. Statut : plan d'exécution, rien de lancé.
Référence fonctionnelle : docs/plan-equilibre.txt (étapes 0-8, D1-D3).
Règles : AGENTS.md (std only, pas d'unsafe, noms explicites, < 1000
lignes par fichier, attentes en ticks, erreurs typées, aucun fallback non
demandé, scripts minces, protocole debug §5, tout en --release).


P. PRÉREQUIS (accord utilisateur)
---------------------------------
P1. Commit du travail du 2026-11-19 (marché 10 %, livraison en pause,
    billets = objet, corrections du jour, docs). Raison : un sous-agent
    isolé travaille dans un git worktree créé depuis HEAD ; sans commit il
    partirait de l'ancien code.
P2. Mesure de référence (lot 0) prise AVANT tout changement : la base de
    comparaison de chaque vague.


R. RÔLES
--------
  - Orchestrateur (session principale) : découpe, lance les sous-agents,
    relit les rapports, fusionne, lance la suite complète, compile,
    déploie (daemon puis workers, un compte à la fois, docs/orchestrator.md),
    mesure. SEUL à toucher au daemon, aux bots et à git main.
  - Développeur (sous-agent, worktree isolé, un par lot) : lit le code du
    lot, écrit D'ABORD le test qui échoue (unitaire ou route en or),
    implémente, fait passer `cargo test --release -p <crates du lot>`,
    met à jour la doc du lot, rend un rapport (fichiers, tests, risques,
    besoin daemon/workers). Jamais de déploiement, jamais de compte
    vivant, jamais de commit sur main.
  - Relecteur (sous-agent, lecture seule, un par lot, NE reçoit PAS le
    raisonnement du développeur, seulement le diff et l'étape du plan) :
    exactitude, effets de bord sur les autres lecteurs du code touché,
    règles AGENTS.md, tests qui prouvent vraiment la règle. Verdict
    OK / À CORRIGER avec file:line.
  - Correcteur : le même développeur relancé (SendMessage) avec les
    remarques du relecteur. Deux allers-retours ratés -> arrêt, rapport à
    l'utilisateur (AGENTS.md §5.6).
  - Mesureur (sous-agent, lecture seule) : 1 h après chaque déploiement,
    compare les indicateurs du lot 0 à la référence, verdict chiffré.


C. CYCLE D'UN LOT
-----------------
  1. Développeur (worktree) : test rouge -> code -> tests du crate verts.
  2. Relecteur : verdict. À CORRIGER -> 3 ; OK -> 4.
  3. Correcteur -> retour en 2 (au plus 2 fois).
  4. Orchestrateur : fusion dans main, `cargo test --release --workspace
     --no-fail-fast` (seuls échecs tolérés : tests de chronométrage nav /
     concurrence store, crates intacts, relancés seuls), build release.
  5. Vague suivante tout de suite : aucune attente ni déploiement entre
     les vagues (décision utilisateur 2026-11-19).
  6. Fin des trois vagues : UN déploiement (daemon puis workers, d'abord
     un bot témoin observé jusqu'au comportement visé, puis la flotte),
     puis le mesureur (1 h, puis bilan des critères M ; un lot qui fait
     reculer un critère est retiré par revert, rapport).

M. CRITÈRES DE RÉUSSITE (mesureur, bilan après la vague C)
--------------------------------------------------------
  - objets cotés des deux côtés >= 35 % (25 % au 2026-11-19) ;
  - écart médian demande/offre <= x1,25 (x2,0) ;
  - objets échangés à 1 pièce en baisse nette (49) ; unités en annonce à
    1 pièce en baisse (1,47 M) ;
  - remplissage < 10 % du temps (20 %) ; if < 10 % (21 %) ;
  - artisanat + magie + cuisine + runes > 10 % du temps (3,2 %) ;
  - lots 100 % marché : réalisé >= 70 % du prévu (16 %).
  Un critère qui recule après un lot -> retour arrière de ce lot.
